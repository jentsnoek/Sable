# Sable development guide\n\n## Goal\n\nHelp people understand and customize League of Legends HUD and champion-skin mods without guessing which of dozens of files to open. Only offer edits that can be safely preserved, and export a new copy without changing the downloaded original.\n\n## Current implementation\n\n- index.html is a browser prototype that opens .fantome and .modpkg packages locally.\n- Files are grouped by readable paths and WAD targets: HUD and interface, champions, maps and environment, audio, package metadata, and other assets.\n- Supported WAD v3 archives can be indexed. Sable detects the contained file type; entries whose path hash cannot be resolved remain named by hash.\n- PNG, JPEG, WebP, GIF, BMP, and selected League TEX textures can be previewed.\n- **Unpack to folder** uses the browser File System Access API to create a fresh workspace directory. package/ preserves the package entries; wad-contents/ contains WAD entries Sable can decode. SABLE-WORKING-COPY.md and SABLE-unpack-report.json explain the layout and list skipped items.\n- Unpacking is not a round-trip editor: this version does not rebuild a .fantome or .modpkg after manual edits.\n\n## Research and recommended architecture\n\nLeagueToolkit describes .modpkg as its recommended package format. Its mod-project layout keeps a project as loose files grouped by layer and target WAD, with a mod.config.json manifest. LeagueToolkit also provides separate Rust crates for project import and packing, .modpkg, legacy .fantome, WAD archives, textures, and hash tables.\n\nThe existing LTK Manager is a useful reference: it is a Windows desktop app built with Tauri, Rust, and React, and supports importing mods, browsing game archives, previewing assets, extracting files, and working with project declarations.\n\n**Recommended direction:** keep the UI simple, but move package and asset handling into a Tauri desktop app with a Rust backend using LeagueToolkit crates. That gives Sable native folder access and a maintained route for real import, WAD, texture, and package operations. Avoid writing independent .fantome, .modpkg, and WAD writers in browser JavaScript.\n\nUse the following pipeline as the app grows:\n\n1. Import .fantome or .modpkg into a loose project.\n2. Build an asset index from layer, WAD target, path, champion, file type, and hash-table matches.\n3. Show only controls supported by the selected asset type.\n4. Validate changed files and package metadata.\n5. Pack a new .modpkg by default, with legacy .fantome export when required.\n\n## Asset organization\n\nUse readable paths when present:\n\n- **HUD and interface:** UI WADs, assets/ux/, HUD atlases, scoreboards, minimaps, ability bars, and related textures.\n- **Champions:** champion-specific models, textures, animations, and data, grouped by champion name.\n- **Maps and environment:** terrain and map assets.\n- **Audio:** banks, sound files, and audio packages.\n- **Package metadata:** author, version, description, layer declarations, and manifests.\n- **Other assets:** files that cannot be confidently identified.\n\nWhen a WAD entry only has a 64-bit hash, group it by its containing WAD and detected type. Resolve the name only when a compatible League path hash table is available; do not guess a champion or HUD part from the hash alone.\n\nThe current unpack folder (package/ and wad-contents/) is an inspection workspace. When the native project importer is added, make the primary editable layout match LeagueToolkit’s content/<layer>/<target-wad>/ convention and keep package-specific details in mod.config.json.\n\n## Priorities\n\n1. Replace the browser-only unpack path with a native project importer backed by LeagueToolkit.\n2. Improve hashed path resolution using official/community hash tables where licensing and redistribution allow it.\n3. Add real editing tools for supported HUD textures and safe asset types.\n4. Repack a new .modpkg, preserving untouched files and metadata; add .fantome output if needed.\n5. Package the stable Windows app as an executable and installer.\n\n## Working constraints\n\n- Keep mod files on the user’s device.\n- Never overwrite the source package or modify the installed League client.\n- Do not bypass anti-cheat or automate game patching.\n- Do not redistribute Riot game assets. Use generated placeholders in the UI.\n- Explain when an entry is unsupported, skipped, or still named by hash.\n\n## References\n\n- [LeagueToolkit mod-package format](https://github.com/LeagueToolkit/docs/blob/main/Mod-Package-Format.md)\n- [LeagueToolkit mod project](https://github.com/LeagueToolkit/league-mod)\n- [LeagueToolkit LTK Manager](https://github.com/LeagueToolkit/ltk-manager)\n- [LeagueToolkit texture crate](https://github.com/LeagueToolkit/league-toolkit/tree/main/crates/ltk_texture)\n- [LeagueToolkit WAD guide](https://github.com/LeagueToolkit/docs/blob/main/WAD-Format.md)\n- [MDN: File System Access API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API)\n\n## Run locally\n\nOpen index.html in a current desktop browser. Zstandard fallback decoding loads fzstd from jsDelivr only when needed; the mod contents stay in the browser.\n
